# B-08 原始／有效轨迹回放查询

对接 C-05。新增只读接口，查询不生成轨迹、不清理暂存点、不修改作业状态、不重新核算面积。沿用现有 PostgreSQL、Elasticsearch，无新增建表脚本。

## 查询方式

`GET /trajectory/playback`，通过正常登录的 Bearer Token 访问。Swagger 的“06-轨迹管理”分组可调试。

| 参数 | 要求 |
| --- | --- |
| `type` | 必填，`ORIGINAL` 原始点，`EFFECTIVE` 已保存有效轨迹 |
| `trajectoryId` | 可选，`trajectory_info.trajectory_info_id`，按原样字符串传递，不转换成数值 |
| `phone` | 未指定作业单时可选，默认当前登录终端；管理员可指定其他终端，普通用户不能指定他人终端 |
| `startTime` / `endTime` | 北京时间，格式 `2026-11-23T08:00:00`；不传作业单时两者必填 |

按作业单查询时，使用作业单绑定终端和起止时间；进行中的作业以本次服务器时间为终点。传入的额外时间范围会与作业时段取交集，手机号若与作业单不符则拒绝。普通用户必须是作业单创建人或其绑定终端，管理员可查询其他作业单。缺少作业单与无权访问返回相同提示，避免泄露存在性。

作业状态口径：`0`进行中、`1`已完成、`2`已逻辑删除；历史空状态保留可查。旧列表与新回放均排除状态2，不再用“只查状态0”来代替未删除筛选。逻辑删除作业即使仍有归档点，也不能通过回放接口查出。

单次时段最长24小时、最多读取50000点、有效轨迹最多涉及200个作业单，超限报错，请分段查询。不会静默截断成前若干条；时间区间包含两个端点，相邻分段查询时可能重复端点，前端可以按坐标和时间去重。

### 示例请求

```text
GET /trajectory/playback?type=ORIGINAL&trajectoryId=<实际作业单号>
GET /trajectory/playback?type=EFFECTIVE&trajectoryId=<同一个实际作业单号>
GET /trajectory/playback?type=ORIGINAL&startTime=2026-11-23T08:00:00&endTime=2026-11-23T09:00:00
```

URL 中的参数应由客户端正常编码。没有历史点时返回成功的空数据；数据源不可用、查询不完整、越权或归档坐标时间不匹配时返回错误，不伪装成“没有轨迹”。

## 返回结构

沿用 `{code,msg,data}`。下面是结构示意，坐标与作业单号均为示例：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {
    "type": "EFFECTIVE",
    "coordinateSystem": "WGS84",
    "timeZone": "Asia/Shanghai",
    "phone": "15888888888",
    "startTime": "2026-11-23T08:00+08:00",
    "endTime": "2026-11-23T09:00+08:00",
    "tracks": [{
      "trajectoryId": "example-order-id",
      "plotId": "9007199254740993",
      "source": "POSTGIS_ARCHIVE",
      "segments": [[
        {"longitude": 114.0, "latitude": 38.0, "time": "2026-11-23T08:00+08:00"},
        {"longitude": 114.001, "latitude": 38.0, "time": "2026-11-23T08:00:01+08:00"}
      ]],
      "pointCount": 2
    }],
    "pointCount": 2,
    "removedDuplicates": 0,
    "skippedInvalid": 0,
    "warnings": []
  }
}
```

实际有效轨迹响应会带数据口径说明，前端应展示 `warnings`。

## 数据来源与处理规则

- **原始轨迹**：来自 GPS 接入写入的 ES 索引。协议微度整数除以1000000，输出 WGS84 十进制度；将带时区的设备时间统一转换为北京时间。通过 scroll 分页读取全部命中点，结束或失败都释放上下文；超时或分片失败报错。每条记录额外核验终端完全匹配。
- **有效轨迹**：来自 `trajectory_points.points` 与 `times`，二者在同一条 SQL 中读取，以 `trajectory_info` 提供作业单、终端和时间范围。恢复坐标与时间一一对应的序列，只移除几何保存时额外添加且无对应时间的闭合点，不把轨迹画成闭合多边形。
- 每条轨迹按时间升序排列，只移除“时间、经度、纬度完全一致”的重复点；同一位置不同时间仍保留，以便表现停留。缺失时间、非有限数值、越界坐标计入 `skippedInvalid` 并给出警告。
- 不同作业单分别返回；同一轨迹点间隔大于5分钟时分段。同一时间对应不同坐标时，将歧义点隔离为独立片段，不推测先后顺序。
- 前端对每个 `tracks[].segments[]` 单独画线，不跨轨迹或片段连线。只有一个点的片段画标记即可。高德显示时需要执行 WGS84→高德坐标转换，数据查询坐标保持 WGS84。
- 原始查询按终端与时间取数，包含进出地块的行驶点，不按地块边界裁剪，也不保证同一时段的原始点只属于该地块。

## 当前有效轨迹的业务口径

此接口返回已有系统保存的有效作业点序列，不是“面积裁剪后所有线段”的新数据集。历史格式可能包含为兼容 Polygon 保存而生成的补点；面积仍以原有边界裁剪和覆盖去重结果为准，前端不能用回放点数或简单连线重算结算面积。

`effective_point_buffer` 是生成轨迹前的暂存点，查询不会触发生成或删除，也不会将其冒充归档轨迹。作业单尚无对应的 `trajectory_points` 时给出明确警告。如果开始／结束作业产生的作业单与轨迹生成器产生的记录使用不同 ID，需要调用方选择实际归档轨迹 ID，或按终端与时间查询相关归档记录；本接口不猜测并绑定不同作业单。

历史数据若已有坐标与时间长度不匹配，会拒绝回放，需另行核对修复。超速、转场等业务异常识别和人工修正属于 B-11／B-12；5分钟分段是显示规则，不是面积核算规则。

## 测试与验收

自动测试使用模拟 mapper 和本机假 ES HTTP 服务，覆盖时间排序、重复点、缺失时间、时区、断点、权限、归档闭合点、损坏数据、分页读取、超时和 scroll 清理，不写共享业务数据。

真实接口验证步骤：

1. 重新构建并重启后端，打开 `http://localhost:8088/swagger-ui.html`，登录授权后找到“06-轨迹管理”的 `GET /trajectory/playback`。
2. 从本人轨迹列表选择一条实际已归档轨迹，先传 `type=EFFECTIVE` 和其 `trajectoryId`。核对点数、时间顺序、片段及 `warnings`。
3. 保持同一个 ID，改为 `type=ORIGINAL`，核对返回来源为 ES、时间范围相同，允许包含地块外点。没有原始记录时应返回空数据，不生成示例轨迹。
4. 普通账号指定其他终端时应返回403；开始晚于结束、超过24小时应返回校验错误。管理员身份的测试不能用于证明普通用户权限正确。
5. C 同学按片段分别画线，再接入播放／暂停等页面控件。B-08 此次交付为查询接口与契约，未新增回放页面。
